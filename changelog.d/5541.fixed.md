- A `CapabilityPolicy` can now express "read broadly, write narrowly" without
  breaking the subprocesses running under it. Three sandbox defects prevented
  it:
  - The process cwd check consulted only `workspace_roots`, so a root granted
    through `process_sandbox` could be handed to a child that was then forbidden
    to start there — making the process-only grant unusable for its documented
    purpose.
  - On macOS a read-only root emitted a trailing `deny file-write*`, and because
    `sandbox-exec` is last-match-wins it silently revoked explicit write grants
    and the standard device rules: a wide read root would deny a child
    `/dev/null`. Explicit grants and the device rules are now re-asserted after
    the deny. The other backends are additive (Landlock rules, Windows ACL
    grants, `unveil`'s longest-prefix match) and were never affected.
  - `signal` is its own `sandbox-exec` operation, so `(deny default)` blocked it
    even with `(allow process*)`. A sandboxed script could not reap a helper it
    had backgrounded, and the orphan held the parent's stdout pipe open — which
    surfaced as a hang rather than a denial. Signalling within the same sandbox
    is now allowed.
- `CapabilityPolicy::intersect` compared filesystem roots as strings, so a
  nested policy narrowing to a subdirectory of a host root matched nothing and
  fell back to the execution root — returning a *wider* scope than either side
  asked for. Roots are now compared by path containment: a narrower request
  stands, a wider one is clamped to the host root.
